# 2D-солитоны

Интерактивные симуляции локализованных нелинейных волн в двух измерениях.
Мышью порождаешь «горбы», они летят и сталкиваются.

```bash
npm start          # http://localhost:8123
```

ES-модули требуют http-происхождения — открыть `index.html` через `file://` не получится.

---

## Существует ли вообще 2D-солитон?

Короткий ответ: да, но выбор уравнений куда беднее, чем в 1D, и большинство
«очевидных» обобщений не работает. Приложение показывает и то, и другое.

**Работает — настоящие локализованные горбы:**

- **KP-I**, `(u_t + 6uu_x + u_xxx)_x − 3u_yy = 0`. Интегрируемо. Lump-солитоны —
  рациональные решения, локализованные по обеим осям, с жёсткой связью
  амплитуда `4μ²` ↔ скорость `3μ²`. Столкновения строго упругие: проходят друг
  сквозь друга и восстанавливают форму. Физически это мелкая вода с сильным
  поверхностным натяжением (число Бонда > 1/3, тонкие плёнки).
- **НУШ с кубично-квинтичной или насыщающейся нелинейностью.** Не интегрируемо,
  но 2D-солитоны («световые пули») устойчивы, летят под любым углом и
  сталкиваются почти упруго.
- **Захаров–Кузнецов**, `u_t + 6uu_x + ∇²u_x = 0`. Плазменный 2D-аналог KdV.
  Устойчивые солитоны, но движение только вдоль `+x` — уравнение анизотропно.

**Не работает — и это половина смысла:**

- **KP-II** (обычная вода). Тоже интегрируемо, но лампов нет вообще: локальный
  горб разваливается в излучение. Живут только линейные солитоны и их
  X-резонансы. Именно поэтому в океане видны длинные гребни, а не бегающие шишки.
- **Кубическое НУШ в 2D** — критический случай. Таунсендовский профиль
  существует, но неустойчив: чуть больше амплитуда — коллапс за конечное время,
  чуть меньше — расплывание.
- **Sine-Gordon в 2D.** В 1D это эталон интегрируемости; в 2D интегрируемость
  теряется, кольцевой кинк схлопывается и умирает от излучения.

Не вошло: **Дэви–Стюартсон I** с её дромионами. Они экспоненциально
локализованы, но держатся на не убывающих на бесконечности фоновых полях вдоль
осей, что требует отдельной постановки — периодический ящик тут не подходит.

## Как пользоваться

- **Клик** по полю — солитон на месте.
- **Клик с протяжкой** — задаёт направление и величину; четверть окна = максимум.
  Что именно означает протяжка, зависит от уравнения: для НУШ это прямо вектор
  скорости, для KP-I — только поперечный наклон (продольная скорость жёстко
  связана с амплитудой), для ZK — величина скорости вдоль x.
- **Сценарии** — готовые конфигурации столкновений.
- **Инварианты** в панели считаются на лету. Если они поехали — шаг слишком
  велик, а не «физика такая».
- `пробел` — пауза, `c` — очистить.

## CPU или GPU

Переключатель «где считать» гоняет ровно те же солверы либо на CPU
(JavaScript, float64), либо на GPU (WebGPU, float32) — модели и интеграторы
об этом не знают, вся разница спрятана за именованными ядрами бэкенда.
Сетки: 128², 256², 512², 1024².

Замерено на интегрированной Radeon (GCN 5), KP-I, мс на шаг:

| сетка | CPU | GPU | ускорение |
|---|---|---|---|
| 128² | 7.9 | 0.34 | 23× |
| 256² | 43.6 | 1.64 | 27× |
| 512² | 209 | 7.4 | 28× |
| 1024² | 1128 | 31.5 | 36× |

1024² на CPU — больше секунды на шаг: это не поломка, это и есть
демонстрация. На GPU та же сетка идёт с плавной картинкой, а 128² успевает
больше 40 шагов на кадр.

Потолок здесь — полоса памяти, а не арифметика: `copy` на этой машине даёт
24 ГБ/с, и шаг KP-I идёт со скоростью 25 ГБ/с, то есть упирается ровно в неё.
Поэтому оптимизация сводилась к «не трогать лишние байты»: FFT2 в три прохода
вместо четырёх, слияние проходов и починка конфликтов банков разделяемой
памяти. Разбор — в [CLAUDE.md](CLAUDE.md).

Одинарная точность на GPU видна в 5–6 знаке инвариантов и накапливается до
~1e-5…1e-4 по полю за сотни шагов. Допустимый шаг она при этом **не**
сокращает: до одного и того же физического времени дрейф ‖u‖² на GPU совпадает
с CPU до знака (это потери на маске 2/3, а не на точности). Числа —
в [CLAUDE.md](CLAUDE.md).

## Проверка

```bash
npm run verify      # лампа KP-I: форма, скорость, инварианты; и что KP-II её рушит
npm run residual    # невязка PDE на аналитическом лампе — определяет знак σ
npm run gpu-check      # GPU против CPU: FFT, все 7 моделей, редукции
npm run gpu-profile    # ГБ/с по каждому ядру — чем упёрлись
npm run gpu-stability  # дрейф инварианта до равного физического времени
npm run bench          # мс/шаг для CPU и GPU на всех сетках, со скриншотами
node tools/smoke-browser.mjs shots           # все модели в браузере, CPU
node tools/smoke-browser.mjs shots gpu 1024  # то же на GPU, сетка 1024²
```

Всё это headless и без флагов запуска: headless-Edge отдаёт настоящий
аппаратный WebGPU-адаптер, а вот `--use-angle=swiftshader` — единственный
флаг, который его отбирает.

Численные результаты и обоснование выбранных шагов — в [CLAUDE.md](CLAUDE.md).

## Устройство

Псевдоспектральные солверы на периодическом квадрате. KdV-типа (KP, ZK) —
ETD-RK4 с φ-функциями через контурный интеграл; НУШ — split-step Фурье;
sine-Gordon — точный поворот линейной части плюс Strang-пинок. Профили солитонов
там, где нет замкнутой формулы, считаются итерацией Петвиашвили.

Весь доступ к данным сетки идёт через именованные ядра в `src/core/backend.js` —
поэлементные, FFT и редукции. Ровно тот же набор имён реализует
`src/core/webgpuBackend.js`: модели и интеграторы про бэкенд не знают.
FFT на GPU держит строку целиком в памяти рабочей группы, столбцы делаются
транспонированием; редукции двухступенчатые и асинхронные. Подробности —
в CLAUDE.md.
